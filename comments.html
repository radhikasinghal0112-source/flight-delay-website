What this project shows about how I work

Each skill is paired with something you can check in the report or the code
Skill Evidence
Investigating data before modelling Noticed that the data files were sorted by a column they never supplied (row position correlated 0.97 with departure time across 334 days), and used it to recover each flight’s departure delay.
Feature engineering The row-order features alone raised every one of seven models by 14 to 18 F1 points. Tuning, a wider search and ensembling together added 0.5 points or less.
Choosing the right objective Tuned for the competition metric (F1) instead of accuracy, and chose the decision cut-off from out-of-fold predictions. That alone lifted the first model from 0.6044 to 0.6407.
Careful evaluation Stratified hold-out, leakage controls inside the pipeline, and three estimates (cross-validation, hold-out, Kaggle) that agree within one point for six of the seven models.
Error analysis Showed that 16% of flights account for 63% of the best model’s errors, and that they cluster where about half of the flights are delayed.
Honest reporting Stated in the report where the result stops: the key feature depends on how the files were assembled, and the hold-out was consulted in two exploratory comparisons.
Communicating results A written report with nine figures, a documented repository with a requirements file, and this site, built so a non-specialist can follow it.

Three decisions worth noticing

  • I treated my best result as a limitation too. The biggest gain came from an artefact of how the files were sorted. I said so plainly and explained what a real system would do instead, rather than presenting the score as a general result.
  • I kept the test honest. Imputation and encoders were fitted on training rows only, labels were never used to build the order-based features, and Kaggle scores were consulted only after models were chosen.
  • I measured what mattered. I added features one group at a time across all seven models, so the claim that features beat algorithms rests on a table, not a hunch.

Scope, stated plainly

This is a course project on a supplied dataset. It is not a production system, and the scores describe how well the models classify flights that have already landed, not how well they forecast. I include that here because I would rather you hear it from me than discover it.

How this website was made

The site is five static pages with no framework and no build step. That keeps it fast, easy to host, and easy for me to explain line by line.

What the site is built with, and why
Part Choice Why
Structure Semantic HTML5: header, nav, main, section, footer Gives the page a clear outline for browsers, search engines and screen readers.
Styling One shared stylesheet, plain CSS, with Flexbox for the header and CSS Grid for the stat tiles and the sliders All five pages stay consistent, and there is no framework to learn or maintain.
Colour A calm sage-green palette: #F2F6EE background, #2F4A34 headings, alternating #DDEAD6 bands Low eye strain over long reading, with strong contrast on every background.
Typography Lora for headings and Nunito Sans for body text, with Georgia and system fonts as fallbacks A serif and sans-serif pairing that reads well, and the page still looks fine if the fonts fail to load.
Interactivity One small vanilla JavaScript file for the sliders on the Finding page No libraries, so there is nothing else to load, and the page works without it.
Figures The report’s vector charts exported to PNG, with width and height set and lazy loading The text does not jump around as images load, and the page loads quickly.
Hosting Static files on GitHub Pages Free, and it deploys straight from the repository.

Accessibility

I wanted the site to work for people who read it in different ways. These are the choices I made, and the checks behind them.

  • Screen readers. Pages use landmark regions and a proper heading order. The current page is marked with aria-current, tables have header cells and captions, and every chart has a text description that includes its key numbers.
  • Keyboard only. Every link, slider and scrollable table or chart can be reached with the Tab key, with a clear focus outline. A “Skip to main content” link appears on the first Tab press so the menu can be bypassed.
  • Low vision. All text meets the WCAG AA contrast ratio of 4.5:1, checked with a contrast calculation, and the lowest pairing is about 4.6:1. Text sizes are relative, line height is generous, and zooming is not blocked.
  • Sliders. Each slider has a visible label and announces its value, for example “5 to 8 min, 62 percent delayed”. Without JavaScript they are hidden and the charts above carry the same numbers.
  • Motion. Transitions are switched off for visitors whose system asks for reduced motion.
  • Phones. I checked the layout at desktop and phone widths. Pages never scroll sideways, and wide charts and tables scroll inside their own box instead.

What I did not test

My checks were a contrast calculation and viewing the pages in a browser at two widths. I have not tested the site with a screen reader or on a range of real devices, so there may be issues I have not found. If you spot one, I would like to know.
