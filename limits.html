Honest caveats and what comes next

What the result does and does not show.

The scores are real, but the key feature comes from how the files were put together. Here is where that limits the conclusions.

Limitations

  • The key feature depends on file order. The file order stands in for the scheduled departure time, which an airline already knows from its timetable. The features make a missing column recoverable; they are not a discovery about what causes delays. They would not carry over to data without that ordering, and a deployed system would read the scheduled departure directly.
  • Several strong inputs are only known late. Elapsed time, air time, wheels-on time and taxi-in time are realised during or after a flight. The scores describe retrospective classification of completed flights, not early forecasting.
  • Features were built before the split. The row-order and pooled features use departure times and positions, never labels, but they are built from the supplied files before the train/hold-out split. The evaluation therefore assumes each day’s flight lists are available at once.
  • Some cases are out of scope. Neither file contains a cancelled or diverted flight, and October is absent, so the models are not validated for either.

How far to trust the numbers

Cross-validated, hold-out and Kaggle estimates agree within one point for six of the seven models, and within 1.6 points for Logistic Regression. They remain estimates. The cut-offs are chosen on the same labels as each cross-validated score, which makes those scores slightly optimistic, and only one random hold-out split was used. The hold-out also informed two exploratory comparisons, so it is not a completely untouched test set.

One simulation suggested that about 0.87 is a practical ceiling for this feature design, because recovering the departure delay perfectly would lift Gradient Boosting from about 0.85 to about 0.87. That is a hypothesis supported by a single experiment.

Where I would take it next

  • Treat each day’s ordered flight list as a sequence and train a transformer to learn the ordering structure directly, instead of hand-building the suffix-minimum and pooling features.
  • Compare tabular transformers with Gradient Boosting.
  • Add real timetable, weather and airport-congestion data.
  • Use nested cross-validation to remove the small optimism from tuning.
  • Test the models on a second year of data to measure how well they transfer.

Run it yourself

The full code, report and figures are in the GitHub repository. The raw data files are not included, because they were supplied for a university assignment and are not mine to redistribute. To run the notebook, place the three course files next to it, then: 

pip install -r requirements.txt
jupyter notebook notebook/flight_delay_models.ipynb

Running all seven models takes about 30 minutes on a two-core machine. The repository is laid out like this: 

notebook/   shared preprocessing, then tuning, cut-off and hold-out for all seven models
report/     full write-up (PDF) and its LaTeX source and figures
figures/    PNG copies of three key charts
requirements.txt
